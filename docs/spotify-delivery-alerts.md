# Spotify automatic delivery and exception alerts

The user requested continued Notion-completion delivery for Everyview and GButs, with missing/failed fulfillment reported through the existing Telegram bot. Existing buyer delivery remains in the guarded platform workers. This change adds an independent read-only monitor in the same server process; it does not create another Codex heartbeat, claim accounts, send test buyer messages, or retry uncertain submissions.

The monitor checks the configured active Everyview Spotify parties and all GButs Spotify listings every60 seconds, using actual active memberships, explicit Notion order bindings, saved seller chat and uncertain-delivery receipts. It sends no account information to an AI service. Completed issued fields use the same delivery formatter as the sender. A saved matching account message is healthy even if the transport acknowledgement remains uncertain. Pending partner work, refunds/cancellations, historical Everyview conversations, old resolved unbound records and intentional safety pauses remain quiet.

Exceptions include completed-but-unsaved delivery, uncertain delivery still absent from saved history, invalid issued details, ambiguous/wrong order binding, a new buyer request missing its Notion record, newly completed/edited Notion rows without a platform order, and repeated source-read failure. Notion edit time is retained for future unbound completions; historic unassigned rows are not guessed or assigned automatically. A provider outage is grouped into one source alert rather than one alert for every sale. Partial failed scans never falsely resolve previously outstanding issues.

An issue must remain observed for at least2 minutes and two scans before notification. The private0600 monitor journal retains only static issue codes, trusted order/page IDs, timestamps and notification state. Telegram payloads contain no account emails, passwords, chat contents, cookies, API keys, credential fingerprints, or raw exception text. Identical incidents notify once across restarts; resolution is quiet, and a new occurrence can notify again. Telegram failure backs off5 minutes rather than being marked successful. The existing seller-alert transport also deduplicates an individual incident key and has bounded fetch/curl timeouts.

Activation uses `SPOTIFY_DELIVERY_ALERTS_ENABLED=true` and the existing seller-alert bot/chat configuration. The default journal is `data/spotify-delivery-monitor.json`; activation is persisted before external reads so restarts retain the baseline. Disabled providers and safe mode suppress their alerts. Everyview notices use the bot's general/system destination; GButs follows its existing trusted provider topic when configured. Normal operation sends no Telegram test or periodic success message.

Verification must include both platform completions and exact issued-field saved-message comparison, pending/historical/refunded silence, persistent missing/uncertain outcomes, unbound future completion detection, provider outage grouping, durable deduplication, failed-notification backoff, quiet recovery and new incidents after recovery. A live read-only preflight must inspect the real current records before enabling alerts. No buyer message or artificial error is created for notification testing.
